# 새 문제 작성과 승인

## 원칙

문제 추가는 실행 중 AI 생성 기능이 아닙니다. 작성자가 신뢰할 수 있는 원문을 직접 열어 확인하고 Git으로 데이터와 검수 이력을 관리합니다. `검증 완료`라는 문자열이나 출처 필드 존재만으로 진실성이 증명되지 않습니다.

## 1. 빈 초안 만들기

프로젝트 폴더에서 아래처럼 실행합니다. ID는 중복되지 않아야 합니다. 예시 ID는 작성 방법을 설명하기 위한 것이며 앱에 샘플 문제를 추가하지 않습니다.

```bat
npm run new:question -- hist-051 한국사
```

`drafts/hist-051.json`이 생깁니다. 현재 ID 001~050은 각 분야에서 사용 중입니다. 질문·보기·해설은 비어 있고 상태는 자동으로 `확인 필요`이며 재검수 승인은 없습니다. 기존 파일이나 은행의 같은 ID는 덮어쓰지 않습니다. 분야는 한국사 / 과학 / 지리 / "예술과 문화" 중 하나입니다. 초안 폴더는 앱에서 불러오지 않습니다.

## 2. 사실 확인과 내용 작성

1. 공공기관·대학·학술기관·박물관·공식 문화기관 등의 자료를 검색하고 원문을 엽니다. 검색 요약이나 개인 블로그만으로 검증을 끝내지 않습니다. 열람하지 못하면 확인 필요 상태로 보류합니다.
2. 정답이 하나로 확정되는 질문을 작성하고 시대·지역·과학 조건을 필요한 만큼 명시합니다. 변동성이 큰 현재 수치·현직 인물·최신 순위는 제외합니다.
3. 네 보기의 ID와 내용을 작성합니다. 정답은 correctOptionId로 연결합니다. 보기 순서를 바꿔도 이 ID는 그대로 유지합니다.
4. 나머지 세 보기가 오답인 이유를 원문에 근거해 기록합니다. 정답을 특정하는 원문에서 논리적으로 배제하는 경우에는 추론임을 분명히 합니다. 동의어·포함 관계가 겹쳐 두 개가 정답이 되지 않게 합니다.
5. 해설은 원문에 근거한 사실만 1~3문장으로 직접 작성합니다. 출처의 문장·이미지를 길게 복제하지 않습니다.
6. sources에 기관명, 실제 문서 제목, 실제 열람 URL, supportedFacts, 원문 위치, 실제 확인일을 넣습니다. 예상 URL이나 확인하지 않은 날짜를 만들지 않습니다.

## 3. 재검수와 은행 반영

1. 질문·정답·오답·해설을 다시 원문에 대조합니다. 조건 누락, 중복, 다른 문제의 정답 노출, 보기 길이 단서도 확인합니다.
2. 해결하지 못한 문제가 있으면 확인 필요 상태를 유지하고 출제 대상에 넣지 않습니다. review.stage3.result를 통과로 바꾸지 않습니다.
3. 실제 확인을 마쳤을 때 verificationStatus를 검증 완료로, review.stage3.result를 통과로 바꾸고 원문 재열람 여부·확인일·판단과 오답별 근거를 작성합니다. 외부 검수자가 없는데 독립 검수를 받았다고 기록하지 않습니다. 기존 문제의 필드 구조를 참고합니다.
4. 편집 중에는 src/data/question-bank.json의 approvedForGameDevelopment를 false로 놓습니다. 검수한 문항을 questions 배열에 추가하고, 관련 docs의 전체 문제·검수 내역도 갱신합니다.
5. 질문·보기·정답·해설·출제 상태가 바뀌면 bankVersion을 현재 1.1.2보다 새 버전(예: 1.2.0)으로 올립니다. 기존 완료 기록은 이전 버전에 남아 별도 순위로 표시됩니다. 수정 없이 버전 이름만 바꾸면 새 순위가 만들어지므로 의도적으로 관리합니다.
6. 모든 필수 내용과 분야별 최소 3개를 확보했을 때만 인계 승인을 true로 변경합니다. 새 출제 내용을 확인한 뒤 검사·테스트·빌드를 실행합니다.

```bat
npm run export:questions
npm run check
```

export:questions는 원본 JSON을 question-bank.md와 question-bank.html로 옮깁니다. 원문을 찾기 쉽게 출처에 searchTerms 배열을 작성하는 것을 권장합니다. 출처에서 실제로 검색되는 단어를 사용합니다. check는 데이터 형식과 승인 필드, 게임 기능을 검사합니다. 프로그램이 사실을 자동 검증하거나 승인자를 인증하지 않습니다. 수정한 원문·검수 판단을 사람이 확인해야 합니다. 앱은 로컬 편집이 가능하므로 승인 필드는 보안 권한 체계가 아닙니다.

## 4. Git 기록

수정한 JSON, 검수 문서, 필요한 테스트를 함께 커밋합니다. 출처가 없어지거나 오류가 발견되면 확인 필요로 되돌리고 버전을 올립니다. 분야별 3개가 안 되면 앱이 시작을 막으며 미검증 문제로 대체하지 않습니다. 앱 코드를 수정하지 않아도 문제 JSON을 바꾸면 개발 실행 시 반영되지만, 빌드 결과를 사용하는 경우에는 다시 빌드해야 합니다.
